   27: 
   28: 	use Mail::Send::DKIM;
   29: 
   30: 	my $dkim = Mail::Send::DKIM->new(

   40: =head1 DESCRIPTION
   41: 
   42: Signs a message with DKIM when its C<From:> domain is one this host signs for,
   43: and hands it to sendmail with whatever arguments sendmail should have.  The
   44: signed form is C<rsa-sha256> with C<relaxed> canonicalization, which is the
   45: shape receiving sites expect.
   46: 
   47: The signature covers the message in the form DKIM defines, where every line
   48: ends CRLF.  What is handed to sendmail is the local form instead: LF line
   49: endings, and no carriage return anywhere, whatever arrived.  A CR would be data
   50: to the MTA that keeps the message - Postfix and Exim both write the CRLF of
   51: SMTP themselves - so a message that had travelled with CRLF in it would reach
   52: the receiver with the CRs doubled and fail the signature it had just been given.
   53: 
   54: Nothing here dies because a key is missing: signing either produces a signed
   55: message or produces nothing and says why on standard error, so a caller can
   56: always fall back to sending the message as it is.
   57: 
   58: =head1 PLATFORMS
   59: 
   60: Windows is not supported.  L<Mail::DKIM> needs L<Crypt::OpenSSL::RSA>, and that
   61: module and its prerequisites, L<Crypt::OpenSSL::Random> and
   62: L<Crypt::OpenSSL::Bignum>, do not link on Windows: Strawberry Perl's static
   63: OpenSSL needs the C<crypt32> library, which their F<Makefile.PL> files do not
   64: ask for.  F<Makefile.PL> stops with C<OS unsupported> there, rather than failing
   65: part-way through the install.
   66: 
   67: =head1 ENVIRONMENT

   70: B<SENDMAIL> are read by B<new> when the corresponding option is not given, so
   71: the command line programs needs no configuration of its own.

  475: =head1 A CRONTAB ENTRY
  476: 
  477: A job that sends mail from cron is where an unsigned message is least likely to
  478: be noticed, so that is usually where this module earns its keep: the program
  479: that ships with it, F<mail-dkim>, is put where the job would have called
  480: sendmail(1), and the job itself is not changed.
  481: 
  482: The weekly summary in this distribution is such a job, and its mail goes out
  483: through F<mail-dkim>.  A crontab line for it looks like this, with the values of
  484: the machine it runs on:
  485: 
  486: 	0 6 * * 1 DMARC_EXPECTED=192.0.2.10 MAIL_TO=alerts@example.org \
  487: 		PERL=/usr/bin/perl /usr/local/bin/dmarc-weekly.sh
  488: 
  489: The three settings are not optional, because cron starts a job with almost no
  490: environment.  C<DMARC_EXPECTED> is what makes a sender nobody expected a
  491: finding, and the run stops with a usage error without it, since guessing would
  492: excuse every sender.  C<MAIL_TO> is where a week that needs looking at is
  493: mailed, and is also the address the alert is sent as unless C<MAIL_FROM> says
  494: otherwise.  C<PERL> has to be an absolute path to a perl that has
  495: C<XML::PP>, as cron's C<PATH> usually holds only the system one; F<--crontab>
  496: fills it in with the first perl on the machine that can load the module.
  497: C<DMARC_DIR> and C<DMARC_ARCHIVE_DIR> are left out of the line because they
  498: default to C<~/Downloads> and C<~/dmarc-archive>.
  499: 
  500: F<dmarc-weekly.sh --crontab> prints that line with the path and the perl filled
  501: in for the machine it runs on, which is more use than an example carrying
  502: somebody else's values; for that reason no example crontab file is shipped or
  503: installed.  A job of your own takes the same shape with F<mail-dkim> in place of
  504: the wrapper: C<DKIM_DOMAINS> and C<DKIM_KEYDIR> say what to sign for, and the
  505: arguments given to it are passed to sendmail(1) as they are.
