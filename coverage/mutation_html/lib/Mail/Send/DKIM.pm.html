   39: =head1 DESCRIPTION
   40: 
   41: Signs a message with DKIM when its C<From:> domain is one this host signs for,
   42: and hands it to sendmail with whatever arguments sendmail should have.  The
   43: signed form is C<rsa-sha256> with C<relaxed> canonicalization, which is the
   44: shape receiving sites expect.
   45: 
   46: The signature covers the message in the form DKIM defines, where every line
   47: ends CRLF.  What is handed to sendmail is the local form instead: LF line
   48: endings, and no carriage return anywhere, whatever arrived.  A CR would be data
   49: to the MTA that keeps the message - Postfix and Exim both write the CRLF of
   50: SMTP themselves - so a message that had travelled with CRLF in it would reach
   51: the receiver with the CRs doubled and fail the signature it had just been given.
   52: 
   53: Nothing here dies because a key is missing: signing either produces a signed
   54: message or produces nothing and says why on standard error, so a caller can
   55: always fall back to sending the message as it is.
   56: 
   57: =head1 PLATFORMS
   58: 
   59: Windows is not supported.  L<Mail::DKIM> needs L<Crypt::OpenSSL::RSA>, and that
   60: module and its prerequisites, L<Crypt::OpenSSL::Random> and
   61: L<Crypt::OpenSSL::Bignum>, do not link on Windows: Strawberry Perl's static
   62: OpenSSL needs the C<crypt32> library, which their F<Makefile.PL> files do not
   63: ask for.  F<Makefile.PL> stops with C<OS unsupported> there, rather than failing
   64: part-way through the install.
   65: 
   66: =head1 ENVIRONMENT
   67: 
   68: B<DKIM_DOMAINS>, B<DKIM_KEYDIR>, B<DKIM_SELECTOR>, B<DKIM_KEYFILE> and
   69: B<SENDMAIL> are read by B<new> when the corresponding option is not given, so
   70: the command line programs needs no configuration of its own.

  372: =head1 A CRONTAB ENTRY
  373: 
  374: A job that sends mail from cron is where an unsigned message is least likely to
  375: be noticed, so that is usually where this module earns its keep: the program
  376: that ships with it, F<mail-dkim>, is put where the job would have called
  377: sendmail(1), and the job itself is not changed.
  378: 
  379: The weekly summary in this distribution is such a job, and its mail goes out
  380: through F<mail-dkim>.  A crontab line for it looks like this, with the values of
  381: the machine it runs on:
  382: 
  383: 	0 6 * * 1 DMARC_EXPECTED=192.0.2.10 MAIL_TO=alerts@example.org \
  384: 		PERL=/usr/bin/perl /usr/local/bin/dmarc-weekly.sh
  385: 
  386: The three settings are not optional, because cron starts a job with almost no
  387: environment.  C<DMARC_EXPECTED> is what makes a sender nobody expected a
  388: finding, and the run stops with a usage error without it, since guessing would
  389: excuse every sender.  C<MAIL_TO> is where a week that needs looking at is
  390: mailed, and is also the address the alert is sent as unless C<MAIL_FROM> says
  391: otherwise.  C<PERL> has to be an absolute path to a perl that has
  392: C<XML::PP>, as cron's C<PATH> usually holds only the system one; F<--crontab>
  393: fills it in with the first perl on the machine that can load the module.
  394: C<DMARC_DIR> and C<DMARC_ARCHIVE_DIR> are left out of the line because they
  395: default to C<~/Downloads> and C<~/dmarc-archive>.
  396: 
  397: F<dmarc-weekly.sh --crontab> prints that line with the path and the perl filled
  398: in for the machine it runs on, which is more use than an example carrying
  399: somebody else's values; for that reason no example crontab file is shipped or
  400: installed.  A job of your own takes the same shape with F<mail-dkim> in place of
  401: the wrapper: C<DKIM_DOMAINS> and C<DKIM_KEYDIR> say what to sign for, and the
  402: arguments given to it are passed to sendmail(1) as they are.
